# Clinic

منصة رعاية طبية حقيقية تربط المرضى بالأطباء والممرضين — حجز عيادات وزيارات منزلية، بلوحات تحكم كاملة للمريض ومقدّم الخدمة والأدمن.

React 18 · TypeScript · Vite · Tailwind CSS · shadcn/ui (مخصّص) · Supabase (Postgres + Auth + Storage + Realtime + Edge Functions) · Mapbox

---

## 1. التثبيت

```bash
npm install
cp .env.example .env.local   # ثم املأ القيم الفعلية (راجع القسم 3)
npm run dev
```

## 2. إعداد مشروع Supabase

1. أنشئ مشروعًا جديدًا على [supabase.com](https://supabase.com).
2. من إعدادات المشروع، انسخ `Project URL` و`anon public key` إلى `.env.local`.
3. اربط الـ CLI محليًا وطبّق كل الـ Migrations:

```bash
npx supabase login
npx supabase link --project-ref YOUR_PROJECT_REF
npx supabase db push
```

هذا يطبّق كل ملفات `supabase/migrations/*.sql` بالترتيب: الجداول، الـ Enums، منع Double Booking، RLS الكاملة، الإشعارات، Storage، وصلاحيات مقدّم الخدمة لرؤية بيانات المريض.

4. (اختياري للتطوير المحلي فقط) لتشغيل نسخة كاملة محليًا عبر Docker:

```bash
npx supabase start
npx supabase db reset   # يطبّق migrations + seed.sql (كتالوج الخدمات الأساسي)
```

5. ولّد أنواع TypeScript المطابقة فعليًا لقاعدتك (يستبدل `src/types/database.types.ts` المكتوب يدويًا بنسخة دقيقة 100%):

```bash
SUPABASE_PROJECT_ID=your-project-ref npm run gen:types
```

## 3. متغيرات البيئة

```env
VITE_SUPABASE_URL=https://xxxxxxxxxxxx.supabase.co
VITE_SUPABASE_ANON_KEY=your-anon-public-key
VITE_MAP_PROVIDER=mapbox
VITE_MAP_API_KEY=your-mapbox-public-token
```

احصل على مفتاح Mapbox من [account.mapbox.com](https://account.mapbox.com/access-tokens) — Token عام (public) يبدأ بـ `pk.`، آمن للاستخدام في Frontend.

**لا تضع أي Secret في `.env` الخاص بالـ Frontend.** المتغيرات أعلاه كلها معلنة (public) بتصميم Supabase وMapbox.

## 4. نشر Edge Function إنشاء حسابات الأطباء/الممرضين

هذه الدالة تحتاج `service_role key` (سرّي تمامًا، **لا يُستخدم أبدًا في الـ Frontend**):

```bash
npx supabase secrets set SUPABASE_SERVICE_ROLE_KEY=your-service-role-key
npx supabase functions deploy admin-create-provider-account
```

بدون هذه الخطوة، زر "إضافة طبيب/ممرض" في لوحة الأدمن لن يعمل.

## 5. إنشاء أول حساب Admin (خطوة يدوية مرة واحدة)

المنصة عمدًا لا تسمح لأي أحد بترقية نفسه لـ Admin (قسم الأمان في المواصفة). لإنشاء **أول** حساب أدمن:

1. سجّل حسابًا عاديًا من `/register` بالبريد الذي تريده كأدمن.
2. من Supabase Dashboard → SQL Editor، نفّذ (بعد استبدال البريد):

```sql
update public.profiles
set role = 'ADMIN'
where id = (select id from auth.users where email = 'admin@example.com');
```

3. سجّل الخروج والدخول مرة أخرى — سيتم توجيهك تلقائيًا للوحة `/admin`.

كل حساب Admin إضافي بعد كده يقدر يُدار عبر تعديل مباشر مشابه من قِبل صاحب المشروع (لا توجد شاشة "ترقية لأدمن" داخل التطبيق نفسه، بتصميم أمني مقصود).

## 6. التشغيل والبناء

```bash
npm run dev        # تطوير محلي — http://localhost:5173
npm run typecheck  # فحص TypeScript فقط
npm run lint       # ESLint
npm run build      # بناء الإنتاج (tsc -b && vite build) → dist/
npm run preview    # معاينة نسخة الإنتاج محليًا
```

## 7. النشر على Vercel

1. ادفع المشروع إلى GitHub.
2. من Vercel: New Project → اختر الـ repo → Framework Preset: **Vite**.
3. أضف نفس متغيرات البيئة من القسم 3 في إعدادات المشروع على Vercel (Environment Variables).
4. Build Command: `npm run build` — Output Directory: `dist` (تُكتشف تلقائيًا لمشاريع Vite).
5. Deploy.

لا حاجة لأي إعداد سيرفر إضافي — كل الـ Backend (قاعدة البيانات، المصادقة، الملفات، الدوال) على Supabase.

## الأمان — ملخّص الطبقات

1. **RLS على كل جدول** (`supabase/migrations/20260909190010_rls.sql` وما بعده) — الطبقة الحقيقية غير القابلة للالتفاف عليها.
2. **Triggers** لفرض قواعد لا تقدر RLS وحدها تفرضها: منع تغيير `role`/`status` ذاتيًا، منع تعديل تفاصيل حجز بعد إنشائه، منع تقييم قبل اكتمال الخدمة، منع انتقال حالة حجز غير منطقي أو من طرف غير مخوَّل.
3. **Exclusion Constraint** على مستوى PostgreSQL لمنع Double Booking فعليًا (وليس فقط في الواجهة).
4. **RPC بصلاحية SECURITY DEFINER** للعمليات الحساسة فقط (ترقية دور، تغيير حالة حساب) مع تحقق `is_admin()` داخلي.
5. **Edge Function منفصلة** لأي عملية تحتاج `service_role` — أبدًا في كود الـ Frontend.
6. **Storage RLS**: كل مستخدم يرفع في مجلده فقط، القراءة عامة للصور فقط.

## الأداء

- Pagination حقيقي (`range()`) في كل قوائم التصفح، لا يتم تحميل كل البيانات دفعة واحدة.
- Debounced Search (350ms) في كل صناديق البحث.
- Indexes على كل الأعمدة المستخدمة في التصفية/الفرز/الربط (راجع الـ Migrations).
- React Query يخزّن النتائج مؤقتًا (`staleTime`) لتقليل الاستعلامات المكرّرة.
- Realtime subscriptions مقصورة على القنوات اللازمة فقط (إشعارات المستخدم الحالي)، مع تنظيف الاشتراك عند مغادرة الصفحة.

## تحسينات التصميم والموبايل (تحديث لاحق)

- مكوّنات موحّدة جديدة (`PageHeader`, `StatCard`) لضمان تناسق بصري احترافي عبر كل لوحات التحكم (مستخدم/مقدّم خدمة/أدمن).
- حالات Hover ناعمة وموحّدة على كل البطاقات (أطباء، ممرضين، حجوزات).
- **إصلاح مهم لصالح الموبايل:** كانت 3 صفحات (حجوزاتي، تفاصيل الحجز، الإشعارات) تطبّق كلاس `container` مرتين (مرة من التخطيط العام ومرة من الصفحة نفسها) — كان بيسبّب حشو جانبي مضاعف يضيّع مساحة الشاشة على الموبايل تحديدًا. تم توحيدها.
- **صفحة الإعدادات** (تغيير كلمة المرور + تسجيل الخروج) بقت متاحة فعليًا لكل الأدوار الأربعة (مستخدم، طبيب، ممرض، أدمن) — مضافة لقائمة الموبايل الجانبية ولقوائم لوحتي مقدّم الخدمة والأدمن على الديسكتوب.
- رابط "رجوع للوحة التحكم" في صفحتي الملف الشخصي والإعدادات يوجّه تلقائيًا للوحة الصحيحة حسب دور المستخدم.

## خدمات وأسعار مقدّم الخدمة (تحديث لاحق)

- صفحة جديدة **"خدماتي وأسعاري"** (`/provider/services`) — الطبيب/الممرض يختار خدماته من كتالوج الأدمن ويحدّد سعره الخاص لكل خدمة (بدل ما يكون فيه سعر واحد ثابت بس)، وده اللي بيظهر فعليًا للمريض في صفحة الحجز والملف الشخصي.
- محمية بـ RLS جديدة: كل مقدّم خدمة يدير خدماته هو بس، مش خدمات غيره.
- أعدت تصميم قائمة تنقّل لوحة مقدّم الخدمة على الموبايل — كانت 4 صفحات (التقييمات، الإيرادات، الخدمات، الإعدادات) مش قابلة للوصول خالص على الموبايل بسبب شريط سفلي بـ 5 عناصر بس. دلوقتي فيه شريط علوي قابل للتمرير لباقي الصفحات، فكل حاجة بقت متاحة على أي حجم شاشة.

⚠️ **Migration جديدة** (`20260909190015_provider_manage_services.sql`) لازم تتطبّق.

## تشديد قواعد الإلغاء + Timeline (تحديث لاحق)

- **قاعدة صارمة جديدة:** الحجز `pending` **لا يمكن إلغاؤه إطلاقًا** — لا من المريض ولا من الطبيب/الممرض، حتى لو حاول أحدهم إرسال `UPDATE` مباشرة متجاوزًا الواجهة (محمي بـ trigger في قاعدة البيانات، مش بس React). الإلغاء يصبح متاحًا فقط بعد `accepted`/`confirmed`.
- **زر إلغاء جديد لمقدّم الخدمة** (لم يكن موجودًا من قبل) — يظهر فقط بعد قبول الحجز، بنفس Dialog التأكيد الأنيق المستخدم عند المريض.
- **إصلاح إشعارات:** لأن الإلغاء بقى متاح للطرفين، عدّلت الـ trigger عشان يبلّغ الطرف اللي *لم يقم* بالإلغاء تحديدًا (قبل كده كان دايمًا بيبلّغ مقدّم الخدمة حتى لو هو نفسه اللي ألغى).
- **Timeline بصري** في صفحة تفاصيل الحجز (مريض ومقدّم خدمة) يوضّح مراحل الحجز خطوة بخطوة، بما فيها مسار الإلغاء/الرفض بشكل مختلف.
- تسميات حالات أوضح بالنص كامل (مش لون بس): "قيد المراجعة"، "تم التأكيد"، "تم الرفض"، "تم الإلغاء"، "اكتمل الموعد".
- رسالة توضيحية بدل زر الإلغاء وقت `pending`: "يمكن إلغاء الموعد بعد تأكيده."
- Navbar بقت تفرّق: المستخدم المسجّل (role=USER) يشوف "حجوزاتي" بدل "كيف تعمل المنصة/عن المنصة".

⚠️ **Migration جديدة إلزامية** (`20260909190016_booking_cancellation_rules.sql`) — من غيرها القاعدة الجديدة (منع إلغاء pending) مش هتتفرض فعليًا على مستوى قاعدة البيانات.

## حالة المشروع

كل المراحل الوظيفية الأساسية (1 حتى 17 حسب خطة `01-architecture.md`) **مكتملة وتعمل فعليًا على بيانات Supabase حقيقية** — بدون Fake Data وبدون Placeholder ثابت في أي تدفّق أساسي، بما في ذلك:
- **"ممرضون قريبون منك"** — ترتيب حقيقي بالمسافة الفعلية (Haversine) ثم التقييم ثم السعر ثم التوفر، بناءً على موقع أساسي اختياري يحدّده الأدمن لكل ممرض (وليس تتبعًا حيًا — قسم 60).
- **"طلب تمريض عاجل"** — قائمة الممرضين المتاحين فعليًا اليوم، مع تنبيه الطوارئ الإلزامي بالنص المطلوب بالضبط.

⚠️ **Migration إضافية جديدة** (`20260909190014_nurse_base_location.sql`) تضيف `base_latitude`/`base_longitude` لجدول `nurses` — لازم تتطبّق زي باقي الملفات.

المتبقي هو صقل إضافي اختياري بحت (اختبارات آلية، تحسينات تصميم دقيقة إضافية) يمكن إضافته تباعًا فوق هذا الأساس الكامل دون إعادة هيكلة.
